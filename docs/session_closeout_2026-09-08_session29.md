## 3. Decisions made

**`E` and `P` are asymmetric, and symmetry was rejected on evidence.** S29-G proposed
`{prefix}E{id}` for employers and `{prefix}P{id}` for participants, on the reasoning that a uniform
`{prefix}{kind}{id}` reads better and keeps the namespaces disjoint. **Four imports disproved the
premise.** The participant field accepts hyphens and the hyphenated value *enrolled successfully* —
clearing the stage where a bad participant key surfaces as `Employer ID Conflict`. Changing a proven
shape would have bought nothing and cost five assertion sites, **one of them an applied migration's
comment that cannot be edited in place**. The employer key alone moved.

**One commit, not two, for T187 + T188 (S29-C).** Both edits landed in the same file and git merged the
`pageEncoding` directive and the T188 heading change into a single hunk. A clean split would have
required `add -p` surgery on a file whose exact UTF-8 bytes had just been verified — real risk for a
cosmetic history benefit. The rule "ship unrelated fixes alone" exists to keep a defect fix out of a
*feature* commit; both of these are defect fixes on the same surface, found and verified together, each
reverting by deleting one line.

**`SUMMIT_BRANCH_CODE` defaults to a real value rather than omitting the column.** `Branch Code` is
mandatory in the template and its entire purpose is to be non-empty. An "omit it when unset" branch
would reintroduce the very defect the column prevents, so an unset or blank key falls back to the
literal `AMS`, and a configured value that sanitizes away to nothing falls back too.

**T187 was fixed per-file, not in `web.xml`.** A `<jsp-config><page-encoding>` would fix every JSP at
once but flips decoding for all of them, including any that carry compensating pre-mangled bytes — a
silent, remote failure mode. A three-label defect does not justify that blast radius. The latent
exposure is filed as T191.

**`Import Plan ID`'s shape was left alone.** It embeds the employer key, so it now reads
`158E140952-ICHRA-2026`. That is a **consequence, not a shape change**, and T185's do-not-touch stands.

## 4. New assumptions

- **Field length limits are undiscovered except one.** `Mailing Address Line 1` caps at **50**
  characters; the same address at **48** was accepted, so it is a plain field-length check rather than
  something subtler. **Name, city, email and every employer-side address field are untested.** The
  element picker does not document lengths. Assume any field may have a limit and expect to find it
  the same way — one import at a time. (T193)
- **Reversal cost of the `E` separator: zero today, permanent tomorrow.** These are upsert keys.
  Nothing real has landed in production; the only employer carrying the old shape is a disposable test
  record. Once a real employer imports, changing the separator orphans it.
- **Summit's file dedupe is content-based, not filename-based.** Assume any re-send of unchanged bytes
  is a no-op regardless of what the file is called. (T194)
- **AMS mirrors what Summit's template dictates and does not negotiate column order.** Mandatory
  elements cannot be reordered in Summit, so the emitter conforms to the template rather than the
  template conforming to AMS.

## 5. Contradictions found

### ⭐ S29-G's premise was wrong, and an import disproved it

S29-G assumed the alphanumeric constraint would generalise from `Employer TPA Custom ID` to
`Participant TPA Custom ID` **because they are "the same family of field."** It does not. **Three
identifiers, three different validations**: the employer key rejects non-alphanumerics, `Import Plan
ID` accepts hyphens, and `Participant TPA Custom ID` accepts hyphens *and survives enrollment*.

Two things went right here and both are worth keeping:

1. **The hard-stop gate caught the entanglement before any code was written.** S29-G's §1 required a
   stop if a third identifier composed from the same prefix turned up. `Import Plan ID` did — built
   *from* `employerTpaCustomId`, so it could not have been left unchanged by the proposed edit. The
   gate did not merely prevent a bad change; it converted a guess into a question.
2. **The answer came from four imports rather than from reasoning**, and the follow-up prompt was
   **smaller** than the one it replaced.

> **The session's reusable lesson: field-level constraints on a third-party system do not generalise
> from one field to its neighbours, and the cost of testing one was a single file.** Reasoning about
> what a vendor "probably" validates produced a wrong answer; uploading a file produced the right one
> in minutes.

### A contradiction this session introduced and then closed

S29-G2's scope fence permitted only `summit_data_exchange.md`'s ID-ownership section. Correct as a
fence — but the *result* was that the file asserted `{prefix}E{prospectId}` in one section and
`{SUMMIT_TPA_ID_PREFIX}-{Prospect.id}` in another. **The change introduced the contradiction rather
than inheriting it.** S29-H closed it in the same session, before the commit shipped. Shipping a doc
that disagrees with itself is worse than shipping a stale one.

### The stale "blocked" claim on File 4

The client-setup File 4 passage still read that Demographics was **blocked** for want of an
AMS-generated employee key. **V094's `employer_participant` roster resolved that**, and the file has
since imported successfully twice. Found in S29-I, deliberately not fixed there (different defect from
that run's two), corrected in S29-J.

### The nine-column Demographics example

The doc carried a nine-column example described as *the test template's element set*. `ZZ_TEST_DEMO`
maps **twelve** elements, so the description was wrong as well as short — and two disagreeing layouts
in one file is how the wrong one gets implemented. Corrected in S29-I.

### S29-A's Case B hard stop

T187 looked like a one-line mojibake fix. The bytes were **already correct UTF-8** (`e2 80 94`,
U+2014); the fault was a missing `pageEncoding`. **The obvious fix would have replaced correct bytes
with wrong ones** and left the real cause in place for the next non-ASCII character anyone typed.

## 9. Next

**Recommended: build the enrollment file emitter.**

The case for it is unusually clean:

- **It is the one gap left in a chain that is otherwise proven.** AMS emits files 1, 2 and 4; the
  fourth file of the proven chain has only ever been hand-built.
- **Its target layout is already import-proven.** The hand-built enrollment file was accepted against
  both a hyphenated and an alphanumeric participant id, and against both plan-id shapes. The emitter
  is not being designed against a guess.
- **It is the step that makes AMS able to set up a Summit client end to end.** Everything before it is
  already automated; this is the last manual artifact in the sequence.
- **Its inputs already exist.** `employer_participant` (V094) holds the roster, and the participant key
  composition is unchanged and proven.

⚠️ **The emitter may need to know which file type it is producing.** `125 PI Elections`, not HRA
Enrollment, is the correct import type for `Ins125` plans — HRA Enrollment covers HRA plans and is not
correct for `Ins125` enrollments. A single "enrollment emitter" that assumes HRA Enrollment would be
wrong for the PremiumPath side of the sale. ⚠️ That correction rests on **Summit vendor AI, 2026-09-07,
never test-verified** — so establishing `125 PI Elections`' real field set by import, the way this
session established everything else, should probably come first or run alongside.

Lower-priority alternatives: T193 (decide where the length guard lives — probably census upload, where
the person can correct the data, rather than export where truncation silently misdirects mail), or
T191's project-wide encoding decision.
