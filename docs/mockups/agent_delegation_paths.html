Agent Delegation — UI Paths (v2)

Three candidate variants of the existing Employee Assignment section on taskManager25.jsp. Agents are internal PSP users with role=2 — they already exist in the user table. The only question is how the eligible-user list is expanded and how the selection is persisted (Task.owner template-level vs ToDo.owner per-Setup).

Current state (for reference)
Employee Assignment
List populated by global.getUsers() — filtered to roles 1/5/9 (PSP User, PSP Admin, PSP Super User). Saves to Task.owner.

Path 1 Expand eligible list — storage level follows entry point

Single existing dropdown. Eligible-user list expands to include agents of the originating agency (resolved via setup.application.proposal.createdBy) when the screen is entered in a per-Setup context. Persistence follows entry point: Sequence Builder writes Task.owner, per-Setup ToDo edit writes ToDo.owner. New column todo.owner_id is added. Completion logic reads ToDo.owner first, falls back to Task.owner.
Employee Assignment
Assigned = visible to them, anyone can complete. Exclusive = only they can complete.
Agents appear in the same list as PSP users — no visual distinction. Users need to know by name who's PSP staff vs an agent.
Pros
Zero UI complexity. One field, one control. Entity change is additive (todo.owner_id). Feels like a natural extension of the existing mechanic.
Cons
Nothing prevents selecting an agent when entered via Sequence Builder — which would pin that agent to every Setup using the Task. No visual signal of who's who.

Path 2 Template default + per-Setup override (one concept, two levels)

Same Employee Assignment concept surfaced at both levels in one card. Top row = Task-template default (PSP-only, cascades to all Setups using this Task). Inline sub-row below = "Override for this Setup" (PSP + agents of originating agency, applies only to this ToDo). The override sub-row only renders in per-Setup context; in Sequence Builder, only the top row shows.
Employee Assignment
Default across all Setups using this task.
Override for this Setup
Applies only to this Setup's ToDo. Agents of the originating agency (ProsperityHSA) appear here.
Top list = PSP-only (unchanged filter). Override list = PSP + agents of originating agency. Same "Employee Assignment" concept — just surfaced at the two levels where it can live.
Pros
Explicit about which level is being edited. User can't accidentally cascade an agent to every Setup — the override row is clearly scoped. Easy to revert ("Use default above"). Good for mixed scenarios (PSP-default, agency-agent on specific Setups).
Cons
Two dropdowns in one section — slightly busier. If PSP default is set, the override relationship must be shown clearly so it's obvious which wins. Doubles the form-submission payload (two whoOwns states).

Path 3 Single dropdown — storage chosen by selected person's role

Recommended. One dropdown as today. Agents never appear in Sequence Builder context — the filter hard-blocks them. In per-Setup context, agents of the originating agency appear alongside PSP users. On save, the server inspects the selected person's role: PSP (1/5/9) writes Task.owner; Agent (2) writes ToDo.owner. Only this last route requires the new todo.owner_id column.
Sequence Builder (Task-template)
Employee Assignment
Template default. Applies to every Setup that uses this Task.
Per-Setup ToDo edit
Employee Assignment
List includes PSP staff and agents of ProsperityHSA (originating agency).
Storage routing is implicit and invisible to the user. If a PSP user picks an agent, save writes ToDo.owner (this Setup only). If they pick a PSP user, save writes Task.owner (all Setups) — with an optional confirmation when this would override an existing ToDo.owner.
Pros
Single control. No Task-level misuse possible by design — agents are filtered out of the template context entirely. Simplest end-user mental model.
Cons
"Same UI, different storage" is a smart behavior that needs clear messaging on save. Two code paths in UpdateTask25 (or a helper) to decide which level to persist to.

All three paths modify only the Employee Assignment section. Ordering, Vendor Sourcing, Links, and Automation sections are unchanged.
