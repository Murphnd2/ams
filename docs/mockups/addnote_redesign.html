Add Note — Redesign Options

Three candidate rearrangements of the PSP-side Add Note widget at the top-right of the activity detail. Goals: put the editor first in the tab order, demote the rarely-used agent-visibility dropdown, and keep the Reason + Status choices close at hand.

Current layout reference

Three dropdowns (Reason, Status, Agent visibility) sit in the SSA-blue header bar, right-aligned. The Quill editor opens below; Save is at the bottom right. First-focus moves through the header dropdowns before reaching the editor.

Tab order: Reason → Status → Agent visibility → Quill editor → Save. The last three dropdowns hijack focus before the primary input.

Option A Summary pills under the editor

Header shrinks to just the title. All three selectors move below the editor as clickable compact pills that open a small popover when tapped. Defaults are shown inline so the user knows exactly what they're about to save without opening anything.

Tab order: Quill → Reason pill → Status pill → Visibility pill → Save. Primary input is first focus.
Pros
Editor is first focus. Current selections remain visible at all times (no "what did I pick?" moment). Visibility pill is greyed to signal "rarely changed." Modest code delta — pills open native-looking dropdowns on click.
Cons
Pills need a popover component (Bootstrap dropdown) — bit more JS than a plain select. Small vertical footprint cost below the editor.

Option B Intent buttons

Replace the dropdowns with a row of "Save as…" intent buttons that bake in the common Reason + Status combos. Typical PSP note flows are a handful of patterns (phone log, email in, email out, internal memo, status check-in) — each button Saves immediately with the right defaults. Advanced customization collapses under a gear. Visibility moves into the gear panel since it's rarely toggled.

Tab order: Quill → Log Call → Email In → Email Out → Internal Memo → More. Enter on any intent button saves immediately with its bundled defaults. No dropdowns in the hot path.
Pros
Fastest happy-path — one click to save as the common cases. Dropdown fatigue gone. Every button is a labeled purpose, not an abstract selector. Agent visibility is genuinely demoted, not just visually shrunk.
Cons
Requires deciding which 3–5 intent buttons to bake in (Reason × Status combos) — a small design exercise. Data migration: existing ddReasons25 values need mapping to buttons; any "exotic" reasons land under More. Extra servlet-side branch to translate intent → (reason, status) tuple.

Option C — refined chosen direction

Editor is first-focus. Reason + Status selects move to the footer next to Save. Agent visibility lives as a single tri-state pill in the header bar, clicked to cycle through Default → Visible → Hidden. It's tabindex="-1" so it never joins the keyboard flow — only a deliberate mouse/click interaction can change it. The pill's color, icon, and label reflect the current state at a glance.

Header-pill states:

Default: Agent: default
After 1 click: Agent: visible
After 2 clicks: Agent: hidden
3rd click: → back to default

Tab order: Quill → Reason → Status → Save. The agent-visibility pill has tabindex="-1" — skipped on Tab, only reachable by mouse/click. The common-case save path is four keystrokes.
Pros
Clean keyboard flow — rarely-touched control is out of the way. Current state is always visible at a glance in the header (color-coded). Tri-state captures all three DB values (NULL default / 1 visible / 0 hidden) without a dropdown. Tiny footprint in the header bar.
Cons
Cycle-toggle affordance is slightly less self-evident than a 3-option select — first-timers might click twice expecting on/off. Mitigated by the color + label changing distinctly per click. Requires a tiny bit of JS to cycle (not much more than a plain select onChange).

Implementation notes: Pill is a <button type="button" tabindex="-1"> with a hidden <input name="agentVisible"> sibling that holds one of "", visible, or hidden. Click handler advances the cycle and updates both the hidden input and the pill's class + icon + label. Servlet read-side is unchanged.

My recommendation

Option B (Intent buttons) gives the biggest UX win for the typical flow — one click per note saves with the right bundle of reason + status. The gear holds the rarely-used knobs. Downside is a small design decision (which 3–5 intents to bake in) and a servlet branch to translate intent → selections.

Option A (Summary pills) is the safest middle ground — no semantic changes to the data model, editor is first focus, defaults are always visible. Good fallback if Option B feels like too large a change.

Option C is the minimum-risk reshuffle. I'd only pick it if you want a quick fix this week and want to revisit later.
